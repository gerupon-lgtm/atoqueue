# mvp-1.32.0 メモ化直後の通知と通知遷移の修正

対象: F-004 / F-006 / F-014 / F-015 / F-017、NF-004 / NF-005 / NF-013。
2026-09-13の利用者承認による修正。実装・ローカル検証と、同日のPWA公開・公開後検証まで完了。

## 修正仕様

- メモ棚卸しの起点を元の登録日時ではなく `Capture.classifiedAt`（メモに分類した日時）にする。日時がない旧メモは `createdAt` にフォールバックする。
- メモ一覧全体で最も早い分類日時を起点にする。週1回は7日後から、月1回は初回14日後・以降UTC暦月ごとという既存間隔を維持する。未整理・タスクの通知規則は変えない。
- 元の登録日時・本文は変更しない。本文編集では起点を変えない。不要から未整理に戻して再度メモに分類した場合は、新しい分類日時を起点とする。
- 既存メモ系列の `seriesKey` が新しい起点と異なる場合、次回の起動・オンライン復帰等の再計算で予約を更新する。同じ位置の予約IDは維持し、余剰枠だけを取消す。既存系列の過去の節目は即時再通知せず未来へ進め、補正後の再起動では再作成しない。
- Pushの既存 `/inbox?reminder=<UUID>` を維持し、端末内 `reminderMap.scope=memo` ならメモタブを表示する。未整理・未知・削除済みのIDは未整理へフォールバックする。タブ閲覧だけでは保存・通知更新をしない。
- 同じ受信箱ウィンドウが開いている場合は、Service Workerが検証済み通知URLを `postMessage` で渡し、React Router内で遷移してからフォーカスする。ページ再読込を避け、未保存の本文ドラフトを維持する。同じ通知IDを再び押した場合もタブを選び直す。画面からの受付応答が1秒以内にない場合・画面が閉じた場合は通常のリンク起動へフォールバックする。タスク通知の起動処理は変更しない。
- 保存schemaVersion=11、通知API v1/v2、DB、Push payload、汎用文面は維持する。新しい保存項目はない。バックアップ内の既存 `classifiedAt` を利用する。

## 実装と検証計画

1. 実際の分類処理で「古い記録をメモ化した直後に通知しない」回帰テストを追加し、失敗を確認する。
2. 起点・系列識別子・旧日時のフォールバックを修正し、既存予約・再分類・月次・本文編集を検証する。
3. 通知IDからのタブ選択と開いている受信箱への通知遷移を修正し、UIとService Workerを検証する。
4. 全単体・結合・E2E、型検査、lint、ビルドを少数ファイルずつ実行する。OS通知は発行せず、ブラウザE2Eでは実際のService Workerのクリックハンドラへ合成イベントを渡す。
5. コードと要件の2軸レビューを行い、証跡・未検証範囲を記録する。公開は別承認。

## 診断根拠と限界

利用者は8月26日登録の未整理を9月13日18:56ごろメモに分類し、19:01には未整理が空だったと報告。ローカル再現では旧処理がメモ化時刻に週次予約1件を作った。匿名配送記録の時刻・間隔とも一致するが、ユーザー端末の予約対応表との完全照合はしていない。

18:56のサーバー送信記録は期限関連であり、未整理放置通知だったとは断定しない。調査・実装時点ではデプロイを含めず、後述の別承認後にPWAのみ公開した。本番予約・設定の手動変更、本番テスト通知は行っていない。

## 別件として検出した既存のバックアップ制約

分類操作が生成する `captureId:capture_classified:<日時>` 等の履歴IDを、バックアップ復元はUUIDではないとして拒否する。今回の通知変更前からある形式不一致で、復元ルールの変更は未承認のため修正していない。保存前のメモリ値には `undefined` が含まれ得るため、検証では通常の保存・読込境界も通す。

今回のバックアップ回帰試験は、従来の復元契約どおりUUID履歴を持つ合成データで `classifiedAt` と次回通知時刻の維持を確認する。任意の実データのバックアップ復元が成功するという保証ではない。
