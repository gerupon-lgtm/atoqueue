## 2. 背景・目的

### 2.1 背景

仕事や日常生活の途中で、別件のアイデア、買い物、食品の期限などを突然思い出すことがある。その場で詳しく整理すると現在の集中が切れ、後回しにすると内容自体を忘れる。一般的なメモへ残しても、見返されず行動につながらない場合がある。

### 2.2 目的

- 思いつきを数秒で安全に退避し、元の作業へ戻れるようにする
- 保存内容を後からタスク、アイデア／記録、不要へ整理できるようにする
- タスクの期限設定と期限切れ後の状態整理を促し、曖昧な放置を減らす
- 放置度に応じて声掛けを変え、完了、新期限、アーカイブのいずれかへ導く

### 2.3 現状手段と反証

| 観点                     | 基準線                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 現状の達成方法           | 【想定】頭で覚える、または一般的なメモへ一時記録する                                |
| 現状の不満               | 思いつきを忘れる、記録しても見返さない、入力時の整理が集中を切る                    |
| 作らない場合             | 忘却、期限切れ、未処理タスクの放置が継続する                                        |
| 利用者ヒアリング         | 現時点では発案者本人1名。第三者利用者への検証は未実施                               |
| 製品全体が不要となる条件 | 7日間の試用で既存手段より記録漏れが減らず、保存から処理までの体験にも改善がない場合 |

## 3. スコープ

### 3.1 MVP対象

- 個人利用
- スマホとPCへインストール可能なPWA
- 端末ごとに独立したローカルデータ
- 一文のクイック入力と受信箱
- ルールベースのタスク候補生成
- 期限設定、期限未設定の再確認、期限切れ処理
- 放置レベルに応じたアプリ内の声掛け
- 最小通知バックエンドからの汎用Web Push
- JSONバックアップと復元

### 3.2 MVP対象外・将来候補

| 対象外・保留項目             | 理由                                     | 再検討条件                                            |
| ---------------------------- | ---------------------------------------- | ----------------------------------------------------- |
| アカウント管理               | 入力とサジェストの価値検証を優先する     | 7日間試用で継続利用価値が確認できたとき               |
| 端末間同期                   | 認証、競合、プライバシー設計が必要になる | 複数端末で同一データを使う需要がMVPの障害になったとき |
| クラウドDBへのタスク本文保存 | MVPでは端末内保存を優先する              | 同期版を設計するとき                                  |
| AIによる文章解析             | API費用、秘密情報、出力不安定性が加わる  | ルールベース候補の精度が継続利用の障害になったとき    |
| チーム共有・他者割当         | 個人の退避と処理に焦点を絞る             | 個人利用の核が安定し、共有需要が確認できたとき        |
| 外部カレンダー連携           | 初期検証に不要                           | 期限管理が安定し、二重管理が課題になったとき          |
| 音声入力                     | 対応差と誤認識処理が増える               | テキスト入力だけでは利用場面が不足すると分かったとき  |
| 位置情報通知                 | PWAとOSの制約が大きい                    | ネイティブ化または対応基盤を検討するとき              |
| バックアップ暗号化           | MVPでは明示操作による平文JSONとする      | 第三者利用または機密データ利用が増えたとき            |

## 4. 用語定義

| 用語             | 定義                                                               |
| ---------------- | ------------------------------------------------------------------ |
| キャプチャ       | 整理せず一文を保存する操作、または保存された元メモ                 |
| 受信箱           | タスク化前のCaptureを、未整理・メモ・不要へ整理する場所            |
| タスク候補       | ルールベース解析が提案するタイトル、期限、カテゴリ。自動確定しない |
| 今日の確認       | 処理が必要な項目を1件ずつ確認するフロー                            |
| 放置レベル       | 期限、経過時間、アプリ内操作履歴から決める声掛け段階               |
| 今回は閉じる     | タスク状態を変えず、後日に再提示する明示操作                       |
| 期限なしタスク   | 利用者が期限不要と明示したタスク                                   |
| 通知予約送信待ち | 通知APIへ未送信の登録、変更、取消操作                              |
| クライアント     | PWAをインストールまたは利用する1つのブラウザ環境・端末             |

## 5. As-Is / To-Be

| 項目           | As-Is                                  | To-Be                                                   |
| -------------- | -------------------------------------- | ------------------------------------------------------- |
| 思いつきの記録 | 覚えておく、別のメモを開く、後で忘れる | PWAを開き一文だけ保存する                               |
| 整理           | 記録時に分類するか、未整理のまま残す   | 入力と整理を分け、後で1件ずつ確認する                   |
| 期限           | 設定し忘れる、期限切れ後も状態不明     | 未設定を3日後に再確認し、期限切れは状態確定まで保持する |
| リマインド     | 一律通知または通知なし                 | 放置レベルに応じた声掛けと具体的な選択肢を示す          |
| データ保全     | メモ先ごとに異なる                     | 端末内保存＋明示的なJSONバックアップを提供する          |

## 6. 想定利用者・体制

| 役割         | 対象                               | 責任・操作                                                   |
| ------------ | ---------------------------------- | ------------------------------------------------------------ |
| 利用者       | 最初は発案者本人                   | 自分の端末のキャプチャ、タスク、通知、バックアップを管理する |
| 開発・運用者 | 【想定】発案者＋AIコーディング環境 | 実装、配布、通知バックエンドの保守を行う                     |

MVPに利用者ロール差、管理者画面、承認フローは設けない。

## 7. 業務要件

| 業務要件ID | 要件                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| B-001      | 利用者は、現在の行動を大きく中断せず思いつきを保存できること               |
| B-002      | 利用者は、保存内容を後から行動対象か記録かに整理できること                 |
| B-003      | 利用者は、期限未設定・期限切れ・放置タスクを曖昧な状態のまま見失わないこと |
| B-004      | 利用者は、タスクの判断を後から安全に修正できること                         |
| B-005      | 通知が届かない場合でも、アプリ内で主要な確認フローを完了できること         |
| B-006      | 利用者は、端末内データを自分でバックアップ・復元できること                 |

### 7.1 初回価値シナリオ

| 対象利用者 | 開始状態               | 最初の価値                     | 最短経路            | 必要な前提                                 | 到達条件                                   | 前提不足時の誘導                     |
| ---------- | ---------------------- | ------------------------------ | ------------------- | ------------------------------------------ | ------------------------------------------ | ------------------------------------ |
| 初回利用者 | データなし・通知未許可 | 一文を保存し受信箱で確認できる | PWAを開く→入力→保存 | 対応ブラウザ。インストールや通知許可は不要 | 保存成功が表示され、再起動後も受信箱に残る | 保存不可理由と対応ブラウザを案内する |

### 7.2 主要リソースのライフサイクル

| リソース   | 生成                                                             | 更新                                   | 取消・削除                                             | 上限                                                 | 重複・競合                             | 復元・監査                |
| ---------- | ---------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------- | -------------------------------------- | ------------------------- |
| キャプチャ | 一文保存で生成                                                   | 元文は保持し、整理状態を更新           | 不要へ移動可能。物理削除は確認後                       | 【想定】5,000件を実用上限の検証対象とする            | 同一文でも別IDとして保存               | JSON復元、操作履歴        |
| タスク     | キャプチャから利用者が確定                                       | タイトル、期限、状態、次回確認日を変更 | アーカイブ・完了取消が可能                             | キャプチャと共通                                     | 同一端末内はUUIDで識別                 | JSON復元、操作履歴        |
| 通知予約   | 受信箱・メモ一覧の全体系列、タスクの期限前・再確認時刻に応じ生成 | 明示保存時または状態変更時に置換       | 全体が空、またはタスク化・完了・アーカイブ時に該当予約を取消 | タスクごとに最大3件、受信箱とメモは各1系列の匿名予約 | リマインダーIDと冪等キーで二重登録防止 | API再送、ローカル送信待ち |
| 操作履歴   | 状態変更時に追記                                                 | 上書きしない                           | MVPでは個別削除しない                                  | 【想定】タスクごと100件を上限検証対象                | 操作IDで識別                           | JSON復元                  |

### 7.3 主要フロー完結性

| フロー           | 開始条件               | 成功時                   | 戻る・取消                               | 失敗時                       | 中断・再開                                   | 二重実行防止                     |
| ---------------- | ---------------------- | ------------------------ | ---------------------------------------- | ---------------------------- | -------------------------------------------- | -------------------------------- |
| クイック入力     | PWAを開ける            | 受信箱へ保存             | 下書きを編集・破棄                       | 入力を保持し再保存           | 下書きから再開                               | 保存ボタンの連打抑止＋ID単位保存 |
| 受信箱整理       | 登録済み項目がある     | タスク、メモ、不要へ分類 | 全分類の元入力文を保持し後から確認・変更 | 現在項目を保持し再試行       | 不要から未整理へ復元、または確認後に完全削除 | 同一項目の状態更新を1回適用      |
| 今日の確認       | 対象タスクがある       | 全件の判断結果を表示     | 「前のタスク」で前回答を変更             | 現在項目を保持               | 未回答から再開                               | 操作IDで履歴重複を防止           |
| 通知予約         | 期限・次回確認日がある | バックエンドへ予約済み   | 変更・取消を再送                         | 送信待ちに保持               | 次回起動・オンライン復帰時に再送             | 冪等キーとPUTで置換              |
| バックアップ復元 | JSONファイルを選択     | 検証後にデータを置換     | 現在データを残して中止                   | 現在データを変更せず理由表示 | ファイル選択から再試行                       | 反映前検証と一括置換             |

### 8.2 主要機能詳細

#### F-002 クイックキャプチャ

- 入力: 1文字以上のUnicode文字列。前後空白だけは保存不可
- 処理: UUIDと作成日時を付け、未整理状態で端末内保存する
- 出力: 保存完了表示と受信箱への追加
- 中断: 入力途中は下書きとして保持する
- PC操作: 初期値ONの「Enterで登録」ではEnterで保存、Shift+Enterで改行。OFFではEnterで改行し、保存ボタンで登録
- スマホ操作: 保存ボタンを主操作とする

#### F-005 ルールベース候補生成

- 日付表現、行動語、買い物・仕事等のキーワードから候補を作る
- 元の入力文を上書きしない
- 候補の自動確定は禁止する
- 解析不能時は候補なしとして、利用者が手動で種別とタイトルを決められる

#### F-008 期限未設定の再確認

- 初回の「まだ決めない」は3日後に再確認する
- 再度「まだ決めない」を選んだ場合も3日後を基本とする
- 3回以上連続した場合は週1回へ抑制し、期限設定または期限なしの判断を促す
- 「期限なしでよい」を選んだタスクは対象外とする

#### F-009 今日の確認

- 対象を1件ずつ表示する
- 見出し「今日の確認」は左揃えとし、右側に矢印なしの「前のタスク」を置く
- 「前のタスク」は先頭では表示せず、2件目以降に表示する
- 進行件数は現在のタスクカード内の右上に表示する
- 回答後は同一画面内で次のカードへ進む
- 中断時は回答済みを保持し、未回答から再開する
- 自動的な「元に戻す」表示は設けない

#### F-011 放置レベル判定

| レベル     | 条件の基準                            | 文面方針                               |
| ---------- | ------------------------------------- | -------------------------------------- |
| 0 通常     | 期限まで余裕                          | 予定の存在を穏やかに示す               |
| 1 確認     | 期限当日、期限未設定の再確認日        | 当日の判断を求める                     |
| 2 放置気味 | 1〜3日超過、またはアプリ内で1回閉じた | 経過事実と状態更新を促す               |
| 3 要整理   | 4〜7日超過、または2回以上閉じた       | 残すか判断するよう促す                 |
| 4 長期放置 | 8日以上超過、延期・無反応が継続       | 完了、新期限、アーカイブの整理を端的に求める |

複数条件に当てはまる場合は最も強いレベルを採用する。OS通知を閉じた事実は放置回数に含めず、PWA内の明示操作だけを使う。

#### F-012 期限切れ処理

- 選択肢: 完了した、今日やる、新しい期限を決める、アーカイブ、今回は閉じる
- 「今回は閉じる」の再提示間隔: 1日後、3日後、7日後、以降7日ごと
- 完了、新期限、アーカイブが確定するまでタスクを保持する
- 責める表現を使わず、経過事実と選択肢を示す

#### F-017 JSONバックアップ・復元

- 書き出し対象: キャプチャ、タスク、操作履歴、設定、通知対応情報
- 除外: Push購読秘密情報と有効なサーバー通知予約
- 復元前に形式、版、必須項目、型、ID、状態、日付を検証する
- 検証失敗時は現在データを変更しない
- 成功時は「復元中止」または「現在データを一括置換」を選ぶ
- MVPではデータ統合と暗号化を行わない

## 12. 稼働環境・前提

- PWAはHTTPSで配信する。localhostは開発用途とする
- iOS/iPadOSではWeb Push利用時にホーム画面追加と利用者の通知許可が必要
- 通知はOS、ブラウザ、集中モード、省電力、通信状態の影響を受け、正確な時刻を保証しない
- 実装はTypeScriptで統一し、PWAと通知APIを同一リポジトリ `gerupon-lgtm/atoqueue` で管理する
- PWAはGitHub Pagesから `https://atoqueue.sikumilab.com` で配信する。Cloudflare DNSはPWA・APIとも最初はDNSのみ（プロキシなし）とする
- 通知APIは構築済みOCI VPSへ配置し、同VPSのPostgreSQLに専用DB `atoqueue_notify` と専用ロール `atoqueue_notify_app` を作成して利用する。スキーマは専用DB内の既定 `public` を使う【想定】
- Fastifyは `systemd` の単一サービスとして `127.0.0.1:3030` で待受し、Caddyが `https://api.atoqueue.sikumilab.com` のHTTPS終端とリバースプロキシを担う
- 本番配置はGitHub Actionsの手動実行・承認を必須とし、専用の配置用SSHユーザーと鍵を使う
- 既存データ移行はない。MVP間の端末移行はJSON復元で行う

## 13. 運用・保守要件

- 通知失敗率、無効購読数、期限超過ジョブ数を確認できるログを残す
- タスク本文、元メモ、具体的な期限内容をサーバーログへ出さない
- 配信失敗は回数制限付きで再試行し、恒久エラーは購読を無効化する
- PWAは起動時に通知送信待ちを再送する
- 端末内データのバックアップは利用者が明示的に実行する。通知DBのOCI Object Storage連携・定期バックアップもMVP対象外とする
- 通知DBを失った場合、PWAは端末登録と有効な通知予約を再作成する。復旧までPushは届かないが、端末内のタスクと「今日の確認」は失わない

## 14. 開発標準提案と例外

| 項目           | 標準提案                     | 採否                 | 変更・例外・理由                                                                        |
| -------------- | ---------------------------- | -------------------- | --------------------------------------------------------------------------------------- |
| バージョン管理 | `mvp-MAJOR.MINOR.PATCH`      | 採用                 | 現在値 `mvp-1.4.0`。設定画面のアプリ情報へ表示する                                      |
| 日付・時刻入力 | ピッカー＋キー入力           | 【想定】変更して採用 | PCは8桁日付→`yyyy/MM/dd`、4桁時刻→`HH:mm`。スマホはネイティブピッカーを優先。秒入力なし |

バージョンは「状態-メジャー.マイナー.パッチ」で管理する。MVP期間の状態は`mvp`とする。単一画面だけを修正し、ドメイン・保存・通知などのロジックを変更しない場合はパッチを上げる。複数画面に及ぶ変更、またはロジック変更を含む場合はマイナーを上げ、パッチを`0`へ戻す。メジャー変更は互換性や利用手順への影響を整理したうえで、発案者へ事前確認する。リリース対象の手入れでは毎回、設定画面、Web/APIの実行バージョン、各ワークスペースのpackage version、設計文書を同じ版へ更新する。

## 15. 成功基準・受入基準

### 15.1 7日間の成功基準

- 思いついてから保存まで概ね10秒以内である
- 入力時に期限・分類を要求されず、元の作業へ戻れる
- サジェスト対象を完了、新期限、アーカイブのいずれかへ整理できる
- 期限切れタスクが黙って消えない
- 通知なしでもアプリ内だけで主要フローを完了できる
- 声掛けが責める印象を与えず、次の行動を選びやすい
- 再起動、オフライン、確認中断で保存済みデータを失わない
- JSONから元メモ、タスク、状態、履歴、設定を復元できる

### 15.2 受入テスト

- 実施者: 発案者本人
- 対象: スマホ1環境、PC1環境。データ同期は検証対象外
- 合格条件: 本書の必須機能IDがトレーサビリティ表の実装タスクと受入試験へ対応し、重大なデータ消失または行き止まりがないこと
- 「処理済み」の定義: 完了だけでなく、新期限またはアーカイブの確定により曖昧な放置状態を解消したこと

## 16. リスクと対応

| リスク                     | 影響                     | 対応                                               |
| -------------------------- | ------------------------ | -------------------------------------------------- |
| localStorage削除・端末故障 | 全ローカルデータ消失     | JSONバックアップ、復元検証、取扱案内               |
| 通知遅延・拒否             | 期限どおりに気づけない   | アプリ内「今日」、機能検出、許可再設定             |
| 過剰通知                   | 通知を無視・解除する     | 1日→3日→7日→週次へ抑制                             |

| API停止                    | 通知予約に失敗           | タスク保存と分離、送信待ち、再試行                 |
| 通知DB消失                 | Push購読・配送待ちを失う | 端末の再登録と有効予約の再同期。端末内データは保持 |
| バックアップ漏えい         | 個人情報流出             | 平文であることを警告し、明示操作だけで生成         |
| 第三者利用未検証           | 発案者以外に合わない     | MVP後に第三者テストを行い、継続条件を再評価        |

## 18. 基本設計への引継ぎ

- 機能ID `F-001`〜`F-018` をトレーサビリティの正典とする
- 非機能要件ID `NF-001`〜`NF-013` を実装タスクへ翻訳する
- MVP機能にロール差はなく、端末所有者のみが自分のローカルデータを扱う
- タスク本文は通知バックエンドへ送らない
- 端末間同期は実装しない
- 「今日の確認」は1件ずつ進み、2件目以降は左揃えの見出し右に置く矢印なしの「前のタスク」で戻る。進行件数はタスクカード内の右上に置く
- 【想定】は基本設計の「前提（仮置き）」へ集約し、確定事項と混ぜない
