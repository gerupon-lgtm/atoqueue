# 通知機能の実装・運用で得た知見

作成日: 2026-08-10

対象コード: `mvp-1.8.0`対応作業時点

目的: 今回の通知調査と改善内容を、次回の通知開発で再利用できる形に集約する。

> この文書の「実装済み」はリポジトリのコードを基準とする。本番環境への配置状態は、この文書の作成時点では再確認していない。

## 1. 結論

- 【確定】通知はOSへ正確な時刻で必ず表示される機能ではなく、忘れ防止を補助する機能である。端末の通知許可、ブラウザ、Pushサービス、省電力、通信状態によって予定時刻の前後に表示される。
- 【確定】通知だけに依存せず、アプリを開いたときに端末内データから「今日の確認」を再計算する。
- 【確定】タスク本文、メモ本文、カテゴリ、期限の意味、ローカルのタスクID・記録IDは通知API、通知DB、ログ、Push payloadへ送らない。
- 【確定】同じ通知種別・同じ予定時刻の予約は、OS上で一つの汎用通知へ集約する。4件のタスクが同じ期限なら、4件の本文を出すのではなく一つの「確認したい項目があります」として知らせる。
- 【確定】通知到達の可能性を高めるため、Web Pushは高優先度、24時間保持、短い振動要求を使う。ただしサイレントモードやOS制限を回避しない。
- 【確定】受信箱の「再通知しない」は、未整理の記録に対する初回通知を1回だけ予約し、その後は繰り返さない。
- 【確定】初回通知前に記録をタスク化した場合、受信箱予約を取消し、タスク用の初回通知は作り直さない。

## 2. 現在の通知経路

```text
端末内で記録・タスク・設定を保存
  -> 端末内で匿名の予定時刻を計算
  -> localStorageのOutboxへupsert/cancelを保存
  -> Push設定済みなら通知APIへ同期
  -> PostgreSQL reminder_jobsへ匿名予約を保存
  -> API起動直後、および5分ごとに配送対象を取得
  -> Web Pushサービスへ汎用payloadを送信
  -> Service WorkerがOS通知を表示
  -> 通知タップで /today または /inbox を開く
```

ローカル保存を先に確定し、通信に失敗しても操作を巻き戻さない。同期失敗時はOutboxへ残し、アプリ再訪時などに再送する。

## 3. 端末側の予約ルール

### 3.1 記録と受信箱

- 【確定】保存直後の記録は、個別ではなく未整理の受信箱全体に対する匿名通知系列へ含める。
- 【2026-09-01更新・確定】系列の基準は最新の未整理記録である。新しい記録を追加したら、その記録にも初回通知を作り、前の初回通知前なら後の時刻へ受信箱全体をまとめる。
- 【2026-09-01更新・確定】初回時刻は「最新の記録日時＋初回通知までの設定分数」で計算する。以前の初回通知済み記録が残っていても、新規記録の初回通知を省略しない。
- 【確定】記録をタスク化、メモ化、不要化、復元、完全削除したときは、保存後の残件を使って受信箱とメモの系列を再計算する。
- 【確定】不要化で未整理が0件になった場合、受信箱系列の予約を取消Outboxへ積む。今回確認された「登録後すぐ不要にしたのに初回通知が来る」問題への対策である。
- 【確定】`inboxReminderFrequency="none"` は初回だけ通知し、その後は再通知しない。ドメインテストで予約が1件だけになることを固定する。
- 【確定】タスク化時は受信箱系列を取消・再構築するだけでなく、タスク側に新しい `initial` を作らない。旧版で作られたタスク所有の `initial` は、次のタスク更新または通知設定保存で取消す。

### 3.2 タスク

有効なタスクには最大2種類の匿名予約を持つ。

| 種類           | 予定時刻       | 現在の条件                                        |
| -------------- | -------------- | ------------------------------------------------- |
| 期限前         | 期限－設定分数 | 設定が1分以上で、計算結果が現在より未来のときだけ |
| 再確認・期限時 | `nextReviewAt` | タスクの通常の確認予定として常に計画              |

- 【確定】期限前通知を0分にすると、独立した期限前予約は作らず、期限時の通常確認予約だけを残す。
- 【確定】タスクには初回予約を作らない。初回通知は未整理の記録にだけ適用する。
- 【確定】期限変更と通知設定変更では、不要になった既存予約を取消し、現在の設定で再構築する。
- 【確定】完了・アーカイブでは、そのタスクに対応する匿名予約をすべて取消す。

### 3.3 メモ

- 【確定】メモも個別予約ではなく、メモ一覧全体で一つの匿名系列を持つ。
- 【確定】最も古いメモを基準にするため、毎日メモが増えても毎日新しい系列を開始しない。
- 【確定】週1回は最古メモの7日後から、月1回は14日後から開始する。
- 【確定】最後のメモを解消したら系列を取消す。

## 4. 配送側で今回改善した点

### 4.1 同時刻通知の集約と上書き防止

以前はすべての通知が固定タグ `atoqueue-review` を使っていたため、後から表示した通知が先の通知を静かに置換する可能性があった。

現在は次の値から匿名の `groupId` を生成する。

```text
SHA-256(notification_type + NUL + scheduled_at) の先頭16桁
```

- 同じ通知種別・同じ予定時刻: 同じタグになり、一つのOS通知へ集約する。
- 通知種別または予定時刻が違う: 別タグになり、先の通知を置換しない。
- `groupId`には本文、タスクID、記録ID、期限内容を含めない。
- 旧Service Workerとの移行期間に備え、`groupId`なしの従来payloadも受理する。

### 4.2 到達性を高める配送属性

現在のWeb Push送信属性は次のとおり。

| 項目                 | 値              | 意味                                                 |
| -------------------- | --------------- | ---------------------------------------------------- |
| `urgency`            | `high`          | Pushサービスへ高優先度配送を要求する                 |
| `TTL`                | `86400`秒       | 端末が一時的にオフラインでも最大24時間配送機会を残す |
| `vibrate`            | `[200,100,200]` | Service Workerから短い振動を要求する                 |
| `silent`             | 指定しない      | アプリ側から無音を強制しない                         |
| `requireInteraction` | 指定しない      | 通知の常駐を強制しない                               |

これらはOSへの要求であり、サイレント／おやすみモード、Androidの通知カテゴリ設定、Chrome/PWAの通知許可、省電力・集中モードを解除するものではない。

### 4.3 5分ポーリングと先読み

- APIは起動時に一度配送処理を行い、その後5分ごとに処理する。
- 一回で最大100件をPostgreSQLの行ロック付きでclaimする。
- `DEADLINE_DELIVERY_LEAD_SECONDS`の初期値は300秒である。次回ポーリングまでの予約を先読みするため、予定時刻より最大約5分前にPush送信を試みる場合がある。
- PushサービスやOS側で保留されれば、実際の画面表示は予定時刻より遅れる場合がある。
- 一時失敗は5分、15分、60分後に再試行し、その後は`failed`にする。
- endpointが404/410なら購読を無効化し、その端末の未配送予約を失敗扱いにする。

## 5. 実機確認から得たこと

- 【確定】ブラウザやPWAの画面を開き続ける必要はない。ただしブラウザの通知権限、OS側のアプリ通知、電池最適化などが配送・表示へ影響する。
- 【確定】利用者が「通知を設定する」を能動的に押し、通知許可、Push購読、匿名端末登録を完了する必要がある。初回起動時に許可ダイアログを自動表示しない。
- 【確定】サイトデータやPush購読を削除した場合は再設定が必要になる。ローカル資格情報、ブラウザ許可、購読の三つを合わせて状態判定する。
- 【確定】Androidの通知履歴に出た「タップすると、このアプリのURLがコピーされます」はChromeのPWA管理通知であり、あとキューのリマインドではなかった。
- 【確定】通知が約2分後に届いた事例は、5分ポーリングと先読みの範囲内で説明できる。
- 【想定】同時刻の期限を持つ複数タスクで通知を確認できなかった事例には、旧固定タグによる置換、PushサービスまたはOS側の遅延・非表示が影響した可能性がある。
- 【要確認】上記事例の発生時点ではDB行と配送ログを保存できなかったため、単一の原因までは確定していない。

### すでにPushサービスへ渡した通知は取消せない

サーバー上で`pending`または`claimed`の予約は取消せる。しかしWeb Pushサービスが受理した後は、タスクを完了・不要化しても、そのPushを回収できない場合がある。現在はTTLが24時間なので、端末がオフラインだった場合などに遅れて汎用通知が届く可能性がある。

通知タップ時にローカルの対応情報がなければ、エラーにはせず通常の「今日の確認」へフォールバックする。次回開発では、到達性と古い通知の抑制のどちらを優先するか、通知種別ごとのTTLも検討対象にする。

## 6. 障害調査の順序

### 6.1 端末で確認する

1. PWAのオリジンが `https://atoqueue.sikumilab.com` である。
2. `Notification.permission` が `granted` である。
3. Service Workerが登録済みである。
4. `pushManager.getSubscription()` が値を返す。
5. ローカル状態に通知端末IDと端末シークレットがある。
6. 設定画面が「この端末は通知設定済みです」と判定する。
7. Android/iOS/WindowsのOS設定でChromeまたはインストール済みPWAの通知が有効で、非表示カテゴリへ入っていない。

画面表示だけで判断せず、許可、購読、ローカル資格情報の三つを分けて確認する。

### 6.2 APIとVPSで確認する

```bash
curl --fail --silent --show-error https://api.atoqueue.sikumilab.com/healthz
sudo systemctl status atoqueue-notification-api.service --no-pager -l
sudo journalctl -u atoqueue-notification-api.service --since '30 minutes ago' --no-pager
sudo ss -ltnp '( sport = :3030 )'
```

期待値:

- `/healthz`がHTTP 200で、DB接続を含めて`status: ok`を返す。
- APIは`127.0.0.1:3030`だけで待受する。
- systemdが`active (running)`である。
- ログに本文、Push endpoint、購読鍵、Bearer、VAPID秘密鍵がない。

### 6.3 PostgreSQLで匿名予約を確認する

調査対象時刻をUTCへ変換してから、次の列だけを見る。

```sql
SELECT
  notification_type,
  scheduled_at,
  status,
  attempt_count,
  claimed_at,
  sent_at,
  last_error_code,
  created_at,
  updated_at
FROM reminder_jobs
WHERE scheduled_at >= '調査開始UTC'
  AND scheduled_at <  '調査終了UTC'
ORDER BY scheduled_at, created_at;
```

| 状態        | 読み方                                               |
| ----------- | ---------------------------------------------------- |
| `pending`   | 未配送。予定時刻、再試行時刻、ポーリングを確認する   |
| `claimed`   | 配送処理中。15分以上ならstale回復対象                |
| `sent`      | Pushサービスへの送信成功。OS表示成功までは意味しない |
| `cancelled` | 端末操作または再計算で取消済み                       |
| `failed`    | 試行上限または購読無効。`last_error_code`を確認する  |

通知DBにはタスクID・本文を保存しないため、DBだけから「どのタスクだったか」は特定できない。これは調査機能の不足ではなく、意図したプライバシー境界である。必要な場合は端末内の`ReminderMap`と`reminderId`を照合する。

## 7. 次回開発へ持ち越す項目

### 優先度高

1. 【要確認】「再通知しない」を本当に「初回だけ」とするかを利用者と再確認する。
2. 決定後、文書・ドメインテスト・`rebuildInboxReminderNotifications`を同時に揃える。
3. 同時刻に4件以上ある場合も、同じ種別は一つに集約され、別時刻・別種別は互いを置換しない回帰テストを維持する。
4. 不要化、完了、アーカイブ、期限変更、通知設定変更で、不要な予約のcancelがOutboxへ残ることを回帰テストで固定する。

### 優先度中

1. 端末内だけで使う「通知診断」表示を検討する。
   - 通知許可、購読、端末登録、Outbox件数、次回匿名予約時刻、直近同期結果を表示する。
   - 本文や秘密値をサーバーへ送らない。
2. 通知種別ごとのTTLを検討する。
   - 期限前通知は短くして古い通知を抑えるか。
   - 受信箱・メモ棚卸しは長く保持するか。
3. Push送信成功数、404/410、再試行、失敗数を、本文なしの集計として運用確認できるようにする。

### 実機受入

- Android Chromeの通常・サイレント・省電力状態
- Windows Chrome/Edgeのブラウザ終了中
- iOSのホーム画面へ追加したPWA
- 同時刻4件、別時刻2件、不要化直後、完了直後、端末オフライン復帰
- 予定時刻、API送信時刻、OS表示時刻を別々に記録する
