# あとキュー → テンパリスト 起動URL連携の送信側設計案

作成日: 2026-09-11。
状態: 利用者確認待ち。本体実装・本番変更は未実施。
受信契約: 利用者が共有した「起動URL連携仕様 v1」、受信側テンパリストv0.4.0。

## 1. 合意済みの範囲

- 複数のTaskを選び、1つのチェックリストの項目として一方向に渡す。テンプレート作成・指定、戻りURL、双方向同期は含めない。
- 初版のコメントは空欄。あとキューにはTask専用のメモ欄がないため、任意項目 `note` を省略する。`Capture.body`（元の記録）は自動転記しない。
- 「連携済」は受信・保存の成功ではなく、あとキューから渡す操作を実行した履歴を表す。受信確認APIは追加しない。
- 表示参考は利用者提供の他アプリの画面。小さなテンパリストのアイコンと「連携済」を、カードの補足情報に淡い背景・細い枠の状態ラベルとして表示する。アイコン未提供時は文字だけとする。
- 元Taskの状態・本文・期限・確認予定・通知予約は変更しない。テンパリスト側で完了・削除されても追従しない。
- Androidを優先。iOSは実機の起動先・保存領域と操作の容易さで判断し、成立しない場合は本連携だけをAndroid限定とする。テンパリスト単体のiOS対応には触れない。
- 通知共通基盤v1/v2のAPI、登録設定、VAPID、DB、Dispatcherは変更しない。

以下の画面・保存方式は、この範囲を実現するための送信側提案であり、受信側へパラメータの追加を要求するものではない。

## 2. 現状と実装時の要件整理

- `packages/domain/src/model.ts` のTaskは `id`、`sourceCaptureId`、`title`、状態・期限等を持つ。専用noteと外部連携記録はない。AppSnapshotはschemaVersion 10。
- `TaskListPage.tsx` は状態・期限・カテゴリ・検索による絞り込みを持つが、複数選択はない。
- `backup.ts` はバックアップ対象を明示列挙している。保存項目の追加だけではバックアップへ自動反映されない。
- F-016（タスク一覧）を入口とし、F-003（端末保存）、F-017（バックアップ）、NF-004/NF-005/NF-006/NF-013の境界を維持する。
- 外部チェックリストへの明示的なコピーはF-019の通知基盤再利用とは別の機能。実装前に `docs/requirements.md` へ専用の機能要件IDを追加し、要件・基本設計・画面・データモデル・タスク表を整合させる。現段階では正典の要件を無断で確定・変更しない。

## 3. 画面と操作

### 3.1 入口

候補は「既存一覧の選択モード」と「独立したタスク選択画面」。検索・カテゴリ絞り込みを再利用できる既存一覧の選択モードを採用案とする。

1. タスク一覧の「チェックリストにする」で選択モードへ入る。
2. 表示中のTaskをチェックして選ぶ。初期表示は既存どおり対応中。完了・アーカイブの絞り込みでも明示選択は可能とする。
3. 絞り込み変更で選択を失わない。表示外の選択も含む総件数を表示する。送信前には必ず全選択項目を確認できる。
4. 「内容を確認」で送信確認画面へ進む。0件では進めない。1件でも受信契約上有効なので許可する。

### 3.2 送信確認

- 初期リスト名は「あとキューのチェックリスト」。利用者が変更でき、空白だけの場合は確定不可。
- 項目の初期順は選択した順とし、上下ボタンで調整する。解除して再選択した項目は末尾へ追加する。
- 項目名は元Taskのタイトルを読み取り専用表示する。項目の除外は可能。元タスクの編集機能や新規コメント入力はここへ追加しない。
- 件数と完成URLの文字数を示す。8000文字を超える場合は「項目を分けて送ってください」と案内し、切り捨てず起動を停止する。
- 「URLには選択したタスク名が含まれます」「元のタスクと通知はあとキューに残ります」を確認できる短い説明を置く。
- 確定前の元Task変更・削除は再読み取りで検知する。古い項目を黙って送信せず、変更内容の確認または選び直しを求める。
- 確定内容を保存できた後だけ「テンパリストで開く」を実行可能にする。保存待ちは多重操作を止め、失敗時は選択内容を保持する。

### 3.3 起動と戻った後

- 利用者操作から固定OriginのURLを開く。自動起動、自動再送、自動クリップボードコピーは行わない。
- 戻り通知はないため、「チェックリストを作成しました」「受信成功」とは表示しない。
- 直前の確定内容には「もう一度開く」を用意し、未保存入力のため受信を中断された場合や、相手側の保存に失敗した場合も同じURLを再利用できる。
- 別リストを作る操作、タイトル・項目・順序の変更は新しい送信操作として扱う。連携済Taskも再度選択できる。

## 4. URLとパラメータ契約

固定の起動先は `https://tempalist.sikumilab.com/#create=<payload>`。

| フィールド           | 送信側での値                     |
| -------------------- | -------------------------------- |
| schemaVersion        | 数値1                            |
| kind                 | `checklist-create`               |
| source               | `atoqueue`                       |
| requestId            | 確定時に発行する小文字のUUID v4  |
| title                | 送信確認画面で確定したリスト名   |
| items[].sourceTaskId | Task.idを変更せず渡す            |
| items[].label        | 確定時のTask.title               |
| items[].note         | 初版は省略。受信側で空文字になる |

- JSONをUTF-8にし、Base64url（末尾paddingなし）で符号化する。日本語文字列を直接btoaへ渡さない。
- 必須値、型、固定値、未知フィールド、項目ID重複を検査する。配列順と同名別IDを保持し、項目名の同一性による統合はしない。
- 期限、カテゴリ、元の記録、Taskの操作履歴、通知資格情報、連携済表示用の時刻・内部データをpayloadへ加えない。
- 制限は完成URL全体で8000文字以内。JSONの文字数や選択件数のみでは判定しない。
- 受信側はrequestIdを小文字化する。同じsource/requestIdでは異なる内容でも既存リストを上書きしないため、送信側でIDと内容を固定する。
- 符号化は暗号化ではない。フラグメントを通信API、アクセス解析、エラーログ、通常のクエリ文字列へ転記しない。URL共有・履歴等による露出の可能性は利用者へ説明する。

受信後の期限未設定・通知OFF・全項目未チェック等は受信側の責務であり、送信側からこれらの初期値フィールドを追加しない。

## 5. 確定内容・再試行・連携済の分離

### 5.1 再試行用データ

保存候補は次の2つ。

- Taskへ連携情報を埋め込む方式: 取得は容易だが、業務上のTask更新と送信操作履歴が混ざる。
- AppSnapshotへ独立した連携領域を追加する方式: 複数Taskをまとめた1操作と、Taskごとの表示を分離できる。

後者を採用案とする。確定payload、生成したURL、確定日時を直前1操作分だけ保持し、Taskごとの「開く操作済み」情報とは独立させる。URLは保存時・読込時に固定Origin、契約、payloadとの一致を検証する。

- 確定しただけでは連携済にしない。
- 同じ操作を再度開く場合は元Taskから再生成せず、保存済みpayloadとURLをそのまま使う。
- 元Taskが後で変更されても、過去の確定内容は書き換えない。最新内容を渡す場合は新しい操作として再選択・確認する。
- 新しい操作を確定した場合、直前操作の再試行データを置き換える。過去の全payloadを無制限に保存する履歴画面は追加しない。
- 再起動・戻る操作では自動起動しない。サイトデータ消去やバックアップ復元で再試行データが失われた場合、同じrequestIdを復元できるとは約束しない。

### 5.2 連携済の意味と表示

Task IDごとに開く操作の時刻とrequestIdを保持する。表示は「一度以上、渡す操作をした」ことを意味し、現在のTask内容が相手のリストと一致するという意味ではない。

| 状況                                    | 表示                                 |
| --------------------------------------- | ------------------------------------ |
| 選択・確認だけ、確定後に開かず戻った    | 付けない                             |
| 入力不正・URL超過・起動前の記録保存失敗 | 新しく付けない                       |
| 有効な内容で開く操作を実行              | 対象Taskへ付ける                     |
| 受信側が中断・保存失敗・キャンセル      | 取り消さない                         |
| 同じ操作を再度開く                      | 同じラベルを維持し、重ねて増やさない |
| 元Taskを編集・完了・再開した            | 過去の操作履歴として維持             |

- 一覧・今日の確認等のTaskカードと詳細で同じ表示定義を使う。主要操作や期限超過表示より目立たせず、ラベルは押せるボタンにしない。
- アイコンがある場合の表示は「小さなアイコン＋連携済」。文字のみでは「テンパリスト連携済」。読み上げでは連携先と「開く操作済み」であることを伝える。
- 起動操作の記録と、受信側の作成を原子的に確定することはできない。ローカルの開く操作受付を永続化してから起動し、アプリ切替前の中断も含め受信成功は意味しない。
- ローカル記録保存に失敗した場合は起動しない。既存の連携済情報・元Taskは保持し、再試行を案内する。
- 実際のリンク起動方式は最小実機試験で決定する。非同期保存後のwindow.openを前提にして利用者操作の権限を失ったり、target指定だけでPWA起動を保証したりしない。

## 6. 保存形式・バックアップの採用案

- 現行schemaVersion 10に対して新しい連携領域を加えるため、実装時にschemaVersionを更新し移行テストを追加する。現時点で次版を仮定する場合は11とし、実装開始時の最新schemaと競合しないか再確認する。
- 旧データは全Task未連携・再試行データなしで移行し、既存Task、Capture、通知予約・資格情報を維持する。
- Task本体のtitle/status/dueAt/nextReviewAt/updatedAt/revision等は連携操作で変更しない。通知OutboxやreminderMapを生成・更新しない。
- バックアップにはTask単位の連携済履歴を含める。復元しても受信成功には読み替えず、移行元での操作履歴として扱う。
- 再起動用の直前payload・URLは端末内の一時的な連携情報としてバックアップから除外し、復元時にクリアする。バックアップを使った端末間の重複防止は保証しない。
- 端末データ削除では連携領域も削除する。削除したTaskの表示用情報を永久保存する仕組みは追加しない。
- 保存アダプターを経由し、UIから直接localStorageを操作しない。連携保存時に古いSnapshot全体で別操作の変更を上書きしないことを、既存の保存・通知同期との結合テストで確認する。

## 7. 実装境界と仕様変更への備え

| 責務                               | 配置候補                                 |
| ---------------------------------- | ---------------------------------------- |
| 選択・確認・並べ替え               | WebのTask一覧と連携確認画面              |
| payload検証とURL符号化             | 専用の独立した純粋モジュール             |
| 確定・再試行・連携済更新           | domain/applicationの連携専用処理         |
| ローカル永続化・移行・バックアップ | 既存repository境界とdomainの移行処理     |
| リンク起動                         | 差替え可能なブラウザ用Port               |
| バッジ表示                         | Taskカードから利用する共通コンポーネント |

受信契約の変更はpayload検証・URL変換・契約fixtureへ集約する。通知共通クライアントへこの機能を混ぜない。テンパリストのソースを製品実行時の依存にせず、今回のローカル参照は契約確認に限定する。

## 8. 検証と公開条件

### 8.1 今回実行した読み取り専用の確認

テンパリストのローカル `package.json` / `src/version.js` は0.4.0。`src/checklist-link.js` の実関数に対して、標準UTF-8/Base64urlで構築した合成データを渡し、次の11観点を確認した。Nodeスクリプトは終了コード0。ファイル保存、localStorage変更、公開先へのリスト作成はしていない。

1. 日本語・絵文字・改行を復元できる。
2. 同名でも異なるsourceTaskIdなら別項目になる。
3. 項目順が維持される。
4. note省略は空文字になる。
5. 大文字UUIDは小文字になる。
6. 未知schemaVersionを拒否する。
7. 未知フィールドを拒否する。
8. 0項目を拒否する。
9. 同じsourceTaskIdの重複を拒否する。
10. 完成URLがちょうど8000文字なら受理する。
11. 8000文字超は拒否する。

これは受信関数との接続前検証であり、あとキュー本体の送信機能、自動保存の排他、公開版の受信画面、OSのPWA起動先を検証した結果ではない。

### 8.2 実装時に追加する自動確認

- 選択・順序・タイトル、空白だけの値、壊れた保存済み連携データ、容量不足。
- 確定時の元Task変更・削除、同一操作再試行、編集時の新ID、同名別ID。
- 未起動時には未連携、起動時に対象だけ連携済、再起動後維持、相手の状態による取消なし。
- 元Task全フィールド、Capture、通知Outbox/reminderMap、既存資格情報の非変更。
- 移行、バックアップと復元、端末データ削除、保存競合。
- 本文やURLが通知API・ログへ出ないこと。リンク起動Portをテスト用に差し替え、実際の利用者データを外部へ渡さず検査する。
- 完了報告前に単体・結合・E2E・型検査・buildを実行し、リリース対象の手入れでは所定の版更新を行う。

### 8.3 実機の先行試験

1. 合成2項目で、あとキューの試験画面からテンパリストへ遷移する。メールやCodexからリンクを開く試験で代替しない。
2. Androidで両PWA起動中・受信側終了時を試す。保存後、普段のテンパリストをホーム画面から開き、同じリストが見えることを確認する。
3. 同一URL再起動と受信側未保存入力からの再試行を確認する。
4. iOSも同じ確認を行う。普段の保存領域へ届かない、または操作が煩雑なら本連携はAndroid限定とし、iOS利用者には非対応を説明する。iOS単体機能は変更しない。
5. 別の受渡し方式やバックエンド経由の本文送信を無断追加しない。
